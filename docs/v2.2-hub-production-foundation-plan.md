# V2.2 Hub 生产化基座实施方案

## 1. V2.2 总目标

V2.1 已经把 skill-q-platform 从 Hub API(资产中心接口) 最小闭环推进到可演示的资产治理平台，覆盖 Asset(资产)、Manifest(清单)、Agent Profile(智能体配置)、审核占位、页面入口和 V1.1 契约保护。

V2.2 的目标是把 V2.1 的“可演示资产治理平台”升级为“可长期保存、可追溯、可多人协作试点”的 Hub(资产中心) 生产化基座：

1. 将当前 HubRepository(资产中心仓储) 内存实现切换为 Prisma Repository(Prisma 数据库仓储)。
2. 将 AuditLog(审计日志) 从内存占位切换为持久化记录。
3. 保持 V1.1 Hub API(资产中心接口)、br-ai-spec(本地 CLI 与消费端契约) 和 V2.1 页面完全兼容。
4. 支持最小多人协作试点，包括最小 RBAC(基于角色的访问控制) 与审核操作留痕。
5. 为后续 V2.3+ 的组织架构、复杂审批、资产工厂和真实执行器接入打基础。

## 2. V2.1 当前状态

V2.1 已达到可验收状态：

1. P0(数据模型与契约保护) 已完成，Prisma schema(数据库结构定义) 已做最小字段增强。
2. P0.5(Prisma migration / seed / generated client 策略) 已完成，并生成 V2.1 governance fields(治理字段) migration(迁移)。
3. P1 Asset 管理 API 已完成。
4. P1.5 Asset API 真实路由核验已完成。
5. P2 Manifest 管理 API 已完成。
6. P3 Agent Profile 管理 API 已完成。
7. P4 Hub 页面已完成。
8. P5 发布流程与审核占位已完成。
9. P6 测试与验收已完成，V2.1 达到可验收状态。
10. V1.1 Hub API 兼容性测试、br-ai-spec-hub-contract(本地消费契约测试)、npm test(测试命令)、next typegen(Next.js 类型生成)、tsc --noEmit(TypeScript 类型检查)、lint(静态检查) 均通过。

当前 V2.1 的核心短板不是功能入口，而是生产化基础：

1. 数据主要依赖内存仓储，服务重启后治理数据不可长期保留。
2. 审计日志为内存占位，不满足追溯要求。
3. 页面展示的是 API 返回结果，但 API 后端尚未切换到真实持久化仓储。
4. 多人协作仅有流程占位，缺少最小权限模型。

## 3. V2.1 已知问题分析

### 3.1 AuditLog 当前为内存占位

当前 AuditLogService(审计日志服务) 使用进程内数组保存状态流转记录。该实现适合 V2.1 演示和测试，但存在以下问题：

1. 服务重启后审计记录丢失。
2. 多实例部署时审计记录无法同步。
3. 无法按 targetType(目标类型)、targetId(目标编号)、operator(操作人)、action(动作)、时间范围进行可靠追溯。
4. 无法满足发布、驳回、归档等关键治理动作的审计要求。

### 3.2 HubRepository 当前为内存实现

当前 HubRepository(资产中心仓储) 以数组维护 assets(资产)、assetVersions(资产版本)、manifests(清单)、manifestVersions(清单版本)、manifestAssets(清单资产绑定)、agentProfiles(智能体配置)、installRecords(安装记录)、runtimeFeedback(运行反馈)。

该实现的主要问题：

1. 数据随进程生命周期消失。
2. 默认 singleton(单例) 仓储不适合多人协作和多实例部署。
3. 列表筛选、分页、唯一性校验依赖内存扫描，数据量增长后不可控。
4. publish(发布)、archive(归档)、bind(绑定) 等多表操作没有事务保护。
5. AssetVersion(资产版本) checksum(校验和) 与 immutable(不可变) 规则依赖服务层约束，缺少数据库层辅助约束。
6. ManifestVersion(清单版本) 绑定多个 AssetVersion 时，缺少数据库事务保证一致性。
7. InstallRecord(安装记录) 与 RuntimeFeedback(运行反馈) 查询仍不适合长期积累。

### 3.3 最小 RBAC 缺失

V2.1 有页面和审核流程，但没有明确的最小角色边界。进入多人试点后，至少需要区分查看者、编辑者、审核者和管理员，否则无法控制谁可以发布、驳回、归档和查看审计记录。

### 3.4 生产化风险集中在兼容性

V2.2 切换持久化时最容易破坏：

1. V1.1 Manifest Export(清单导出) 响应结构。
2. Asset Content(资产内容) 响应结构。
3. Agent Profile Export(智能体配置导出) 响应结构。
4. ApiResponse(统一响应结构) 的 success / data / error / requestId / timestamp 字段。
5. Runtime Feedback(运行反馈) 的隐私拒绝规则。
6. published(已发布) 资源不可变规则。

## 4. V2.2 不做什么

V2.2 只做生产化基座，不做以下内容：

1. 不做 AI 工程资产生成器。
2. 不做真实 Codex(代码智能体) / Cursor(代码编辑器) / Claude Code(代码智能体) 自动编码。
3. 不做 OpenClaw(自动化平台)。
4. 不做钉钉机器人。
5. 不做复杂组织架构。
6. 不做复杂 RBAC(基于角色的访问控制)。
7. 不做复杂审批队列。
8. 不做自动 PR(拉取请求) / push(推送) / merge(合并)。
9. 不重构 V2.1 页面整体视觉。
10. 不改变 V1.1 Hub API 响应结构。
11. 不放宽隐私校验、checksum(校验和) 校验、published(已发布) 不可变策略和 Agent Profile(智能体配置) 安全策略。

## 5. HubRepository 当前内存实现问题

当前 HubRepository(资产中心仓储) 的问题可以归纳为四类。

### 5.1 数据持久化问题

1. 资产、版本、清单、绑定、智能体配置、安装记录、运行反馈均在进程内维护。
2. 服务重启、热更新或多实例部署会造成数据丢失或不一致。
3. 当前 seed(种子数据) 适合测试，不适合作为生产数据来源。

### 5.2 一致性问题

1. AssetVersion 发布时需要同时更新 version.status、version.immutable、version.publishedAt、asset.latestVersionId、asset.status，目前没有数据库事务。
2. ManifestVersion 发布时需要校验所有绑定 AssetVersion 并更新 Manifest.latestVersionId，目前没有数据库事务。
3. 审核提交、驳回、发布和审计记录写入之间没有原子性。

### 5.3 查询能力问题

1. keyword(关键词)、status(状态)、kind(类型)、scope(范围)、riskLevel(风险等级) 等筛选依赖内存过滤。
2. page/pageSize(分页参数) 在数据量增大后性能不可控。
3. InstallRecord / RuntimeFeedback 查询无法按业务字段建立索引。

### 5.4 接口耦合问题

1. 多个 service(服务) 直接依赖 HubRepository 的数组字段。
2. route(路由) 层通过 defaultHubRepository(默认仓储单例) 注入服务。
3. 测试依赖内存仓储便利性，切换 Prisma(数据库 ORM) 时需要保留测试适配器。

## 6. Prisma Repository 目标设计

V2.2 目标不是在 service(服务) 内直接到处调用 Prisma Client(Prisma 客户端)，而是引入 Repository Port(仓储接口) + Repository Adapter(仓储适配器)。

### 6.1 分层目标

建议形成以下结构：

```text
Route(路由)
  -> Service(业务服务)
    -> Repository Port(仓储接口)
      -> Prisma Repository(Prisma 数据库仓储)
      -> InMemory Repository(内存测试仓储)
```

### 6.2 仓储接口建议

按领域拆分，避免一个巨型仓储继续膨胀：

1. AssetRepositoryPort(资产仓储接口)。
2. ManifestRepositoryPort(清单仓储接口)。
3. AgentProfileRepositoryPort(智能体配置仓储接口)。
4. TelemetryRepositoryPort(遥测仓储接口)，覆盖 InstallRecord 和 RuntimeFeedback。
5. AuditLogRepositoryPort(审计日志仓储接口)。
6. HubRepositoryFacade(资产中心仓储门面)，用于兼容现有服务构造方式的过渡。

### 6.3 Prisma Repository 设计原则

1. 所有跨表写操作使用 `$transaction`(数据库事务)。
2. 所有返回给 API 的对象通过 mapper(映射器) 转换，保证 V2.1 响应结构不变。
3. 所有 JSON 字段在进入数据库前做 schema(结构) 校验或最小类型校验。
4. 所有敏感字段在写入前由 PrivacyFilter(隐私过滤) 或服务校验拦截，不把 sourceCode / rawPrompt / rawResponse / 绝对路径写入数据库。
5. 保留 InMemory Repository(内存仓储) 作为单元测试和快速 fixture(测试夹具)。
6. 通过环境配置或依赖注入选择 Prisma Repository(Prisma 仓储)，不要在 service(服务) 中写死实现。

## 7. AuditLog 持久化设计

### 7.1 目标

AuditLog(审计日志) 在 V2.2 必须从内存占位升级为持久化记录，覆盖：

1. submit-review(提交审核)。
2. reject(驳回)。
3. publish(发布)。
4. deprecate(废弃)。
5. archive(归档)。
6. bind / unbind / reorder(绑定、解绑、排序)。
7. security-validate(安全校验) 失败或关键拦截。

### 7.2 建议模型

建议新增 `HubAuditLog` 模型，字段规划：

```text
id String @id
targetType String
targetId String
targetSlug String?
targetVersion String?
action String
statusFrom String?
statusTo String?
operatorId String?
operatorName String?
operatorType String?
reason String?
note String?
metadata Json?
requestId String?
createdAt DateTime
```

建议索引：

```text
@@index([targetType, targetId, createdAt])
@@index([action, createdAt])
@@index([operatorId, createdAt])
@@index([createdAt])
```

### 7.3 写入策略

1. 状态流转和审计写入必须在同一个事务中完成。
2. 审计写入失败时，默认阻断关键发布动作，避免“已发布但无记录”。
3. 查询接口继续使用 `/api/hub/admin/audit-logs`，响应结构保持 V2.1 约定。
4. metadata(元数据) 不允许保存 content(正文)、sourceCode(源码)、rawPrompt(原始提示词)、rawResponse(原始响应) 和绝对路径。

## 9. AssetVersion 持久化映射方案

当前 Prisma schema 已有 `HubAssetVersion` 模型，可承载 AssetVersion(资产版本)。

### 9.1 字段映射

1. `id` -> version.id。
2. `assetId` -> 所属 Asset。
3. `version` -> 版本号，同一 assetId 下唯一。
4. `content` -> 资产正文。
5. `contentFormat` -> markdown / json / yaml。
6. `checksum` -> sha256(哈希校验)。
7. `status` -> draft / reviewing / published / deprecated / archived / rejected。
8. `immutable` -> published 后必须为 true。
9. `qualityScore` -> 质量分。
10. `dependencies` / `compatibility` -> Json。
11. `changelog` -> 变更说明。
12. `source` -> 来源。
13. `contentSize` -> 内容长度。
14. `previousVersionId` -> 前序版本。
15. `publishedAt` / `publishedBy` -> 发布信息。
16. `rejectedAt` / `rejectedReason` -> 驳回信息。
17. `createdBy` -> 创建人。

### 9.2 持久化规则

1. 创建版本时计算 checksum 和 contentSize。
2. draft(草稿) 可以修改 content，修改后重新计算 checksum。
3. reviewing(审核中) 默认不修改 content，只允许发布或驳回。
4. published(已发布) 不允许修改 content，immutable 必须为 true。
5. deprecated(已废弃) 不删除 content，不改变 checksum。
6. archived(已归档) 不允许新绑定。

### 9.3 事务要求

发布 AssetVersion 时必须在事务中完成：

1. 重新计算并校验 checksum。
2. 更新 HubAssetVersion.status / immutable / publishedAt / publishedBy。
3. 更新 HubAsset.latestVersionId / status。
4. 写入 HubAuditLog。

## 11. ManifestVersion 持久化映射方案

当前 Prisma schema 已有 `HubManifestVersion` 模型，可承载 ManifestVersion(清单版本)。

### 11.1 字段映射

1. `id` -> version.id。
2. `manifestId` -> 所属 Manifest。
3. `version` -> 版本号，同一 manifestId 下唯一。
4. `checksum` -> 清单校验和。
5. `status` -> draft / reviewing / published / deprecated / archived / rejected。
6. `installPolicy` -> Json，默认 defaultExecutor=cursor。
7. `compatibility` -> Json。
8. `changelog` -> 变更说明。
9. `previousVersionId` -> 前序版本。
10. `exportSchemaVersion` -> 导出结构版本。
11. `publishedAt` / `publishedBy` -> 发布信息。
12. `rejectedAt` / `rejectedReason` -> 驳回信息。

### 11.2 checksum 策略

ManifestVersion checksum(清单校验和) 需要基于稳定序列化后的以下信息计算：

1. manifest slug。
2. manifest version。
3. installPolicy。
4. compatibility。
5. 绑定资产列表，按 order 升序。
6. 每个绑定资产的 assetSlug、assetVersion、kind、checksum、required、loadWhen、stage、policy。

不得把 AssetVersion content(资产正文) 直接纳入 ManifestVersion checksum 输入；ManifestVersion 依赖 AssetVersion checksum。

### 11.3 发布规则

发布 ManifestVersion 必须在事务中完成：

1. 校验至少一个 required asset(必需资产)。
2. 校验所有绑定 AssetVersion 是 published 且 immutable=true。
3. 校验所有绑定 AssetVersion 有 checksum。
4. 重新生成 ManifestVersion checksum。
5. 更新 ManifestVersion.status / publishedAt / publishedBy。
6. 更新 Manifest.latestVersionId / status。
7. 写入 HubAuditLog。

## 12. ManifestAsset 绑定关系持久化方案

当前 Prisma schema 已有 `HubManifestAsset` 模型，可承载 ManifestAsset(清单资产绑定)。

### 12.1 字段映射

1. `id` -> bindingId。
2. `manifestVersionId` -> 所属 ManifestVersion。
3. `assetId` -> 资产。
4. `assetVersionId` -> 绑定资产版本。
5. `kind` -> 资产类型，必须与 Asset.kind 一致。
6. `required` -> 是否必需。
7. `loadWhen` -> 加载条件。
8. `order` -> 顺序。
9. `alias` -> 别名。
10. `reason` -> 绑定原因。
11. `stage` -> 阶段。
12. `policy` -> 策略。
13. `addedBy` / `addedAt` -> 绑定人和时间。

### 12.2 持久化规则

1. 只能给 draft / reviewing ManifestVersion 绑定、解绑、排序。
2. 只能绑定 published AssetVersion。
3. deprecated AssetVersion 不允许新绑定，但旧 lock(锁定文件) 是否可继续消费由 Manifest Export 兼容策略决定。
4. archived Asset 不允许绑定。
5. 同一个 ManifestVersion 不允许重复绑定同一个 AssetVersion。
6. 绑定、解绑、排序后必须重新计算 ManifestVersion checksum。
7. published ManifestVersion 的绑定关系不可直接修改。

## 13. AgentProfile 持久化映射方案

当前 Prisma schema 已有 `HubAgentProfile` 模型，可承载 AgentProfile(智能体配置)。

### 13.1 字段映射

1. `id` -> profile.id。
2. `slug` -> profile.slug。
3. `name` -> profile.name。
4. `version` -> profile.version。
5. `description` -> 描述。
6. `content` -> Json 内容。
7. `checksum` -> 内容校验和。
8. `status` -> draft / reviewing / published / deprecated / archived / rejected。
9. `ownerOrgId` / `ownerTeamId` / `ownerUserId` -> 归属。
10. `riskLevel` -> low / medium / high。
11. `createdBy` / `publishedBy` -> 操作人。
12. `publishedAt` / `deprecatedAt` / `archivedAt` -> 生命周期时间。

### 13.2 需要评估的最小字段

V2.1 服务层支持 rejectedAt / rejectedReason(驳回时间和原因) 语义，但当前 `HubAgentProfile` Prisma 模型没有对应字段。V2.2 有两种方案：

1. 推荐方案：补充 `rejectedAt DateTime?`、`rejectedReason String?`、`rejectedBy String?`，便于页面直接展示驳回原因。
2. 保守方案：驳回原因只写入 HubAuditLog，AgentProfile 本表只保存 status=rejected。

建议 V2.2 P0 确认后在 P1 或 P2 migration(迁移) 中最小补齐，避免页面状态来源分散。

### 13.3 安全策略

AgentProfile 持久化前必须继续校验：

1. deniedTools 必须包含 upload-source、deploy、push、merge。
2. contextScope.allowSourceCode 必须为 false。
3. contextScope.allowAbsolutePath 必须为 false。
4. approvalPolicy.beforePush 必须为 true。
5. approvalPolicy.beforeMerge 必须为 true。
6. approvalPolicy.highRiskAlwaysManual 必须为 true。
7. content 中不得包含 sourceCode、rawPrompt、rawResponse、绝对路径、apiKey、password、token、secret、`.env` 内容。

## 14. InstallRecord 查询持久化方案

当前 Prisma schema 已有 `HubInstallRecord` 模型，并包含冗余查询字段：

1. manifestSlug。
2. manifestVersion。

## 16. 最小 RBAC 设计

V2.2 只做最小 RBAC(基于角色的访问控制)，用于多人协作试点，不做复杂组织架构。

### 16.1 角色

建议角色：

1. `hub-viewer`：只读查看资产、清单、智能体配置、安装记录、运行反馈。
2. `hub-editor`：创建 draft(草稿)、更新 draft、提交审核。
3. `hub-reviewer`：驳回、审核通过发布、废弃。
4. `hub-admin`：归档、管理权限、查看审计日志。

### 16.2 权限矩阵

| 能力 | hub-viewer | hub-editor | hub-reviewer | hub-admin |
| --- | --- | --- | --- | --- |
| 查看列表和详情 | 是 | 是 | 是 | 是 |
| 创建草稿 | 否 | 是 | 是 | 是 |
| 更新草稿 | 否 | 是 | 是 | 是 |
| 提交审核 | 否 | 是 | 是 | 是 |
| 驳回 | 否 | 否 | 是 | 是 |
| 发布 | 否 | 否 | 是 | 是 |
| 废弃 | 否 | 否 | 是 | 是 |
| 归档 | 否 | 否 | 否 | 是 |
| 查看审计日志 | 否 | 否 | 是 | 是 |

### 16.3 实现策略

1. 优先接入现有登录态或管理后台用户上下文。
2. 暂不实现复杂组织树。
3. 权限检查放在 service(服务) 层，route(路由) 层只解析用户上下文。
4. 所有拒绝返回中文错误。
5. 权限拒绝必须写入审计日志或安全事件日志。

### 16.4 数据模型建议

如当前项目没有可复用权限模型，建议新增最小表：

```text
HubRoleAssignment
- id
- userId
- role
- scopeType
- scopeId
- createdBy
- createdAt
```

V2.2 只使用 role(角色) 和 scope(范围) 基础字段，不扩展复杂策略引擎。

## 17. migration 规划

### 17.1 预计需要的 migration

## 23. 风险点

1. Repository 接口抽象不充分，导致 service 仍依赖内存数组。
2. Prisma 查询返回结构和 V2.1 API 响应结构不一致。
3. JSON 字段类型不稳定，导致 checksum 不稳定。
4. ManifestVersion 发布事务不完整，造成绑定关系和 checksum 不一致。
5. AuditLog 持久化失败但业务状态已变更。
6. AgentProfile 安全策略在写入数据库前未统一校验。
7. Runtime Feedback 隐私校验被数据库写入绕过。
8. MySQL / MariaDB(JSON 与索引行为) 和本地测试数据库差异。
9. seed 不幂等，导致重复数据。
10. 页面真实数据为空时误判为功能失败。
11. 最小 RBAC 接入不当，影响现有本地开发和测试。
12. 历史 lint warning(静态检查警告) 掩盖新增 warning。

## 26. 第一批建议开发任务

进入 V2.2 P1 前，建议先完成以下准备：

1. 确认运行时数据库类型和本地开发数据库连接方式。
2. 确认是否保留 `HUB_REPOSITORY_MODE=memory|prisma` 这类仓储模式开关。
3. 定义 Repository Port(仓储接口) 最小方法集。
4. 为 Asset / Manifest / AgentProfile 各选一个只读查询作为 Prisma Repository 首个切换点。
5. 补充 Repository contract test(仓储契约测试)，同一组测试同时跑 InMemory 和 Prisma 实现。
6. 明确 HubAgentProfile 是否在 V2.2 补 rejectedAt / rejectedReason / rejectedBy。
7. 明确 AuditLog 持久化 migration 命名和字段清单。

结论：V2.2 可以进入 P1 代码开发，但 P1 必须先做 Repository Port(仓储接口) 和 Prisma Repository(Prisma 数据库仓储) 基础设施，不应直接在现有 service(服务) 中散落 Prisma Client(Prisma 客户端) 调用。
