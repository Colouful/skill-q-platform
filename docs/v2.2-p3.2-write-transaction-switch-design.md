# V2.2 P3.2 写事务切换设计与事务边界确认

## 1. P3.2 总目标

P3.2 只做写事务切换设计，不写功能代码。目标是在进入 P3.3 之前，把 Asset(资产)、Manifest(清单)、Agent Profile(智能体配置) 和 Review Workflow(审核流程) 的写事务边界设计清楚，避免把 V2.1 的内存写链路直接硬切到 Prisma Repository(Prisma 仓储) 后产生数据不一致。

当前关键风险必须先明确：

```text
读链路已支持 prisma，但写链路仍是 memory。
如果直接开启 HUB_REPOSITORY_MODE=prisma，会出现读写数据源不一致。
```

不能直接切写事务的原因：

1. 当前写服务大量直接修改 `HubRepository`(Hub 内存仓储) 数组对象，缺少 Repository Port(仓储接口) 写方法。
2. Asset Version(资产版本) 发布、Manifest Version(清单版本) 发布、Manifest Asset(清单资产) 绑定等操作涉及多表更新，必须有事务。
3. AuditLog(审计日志) 已支持 Prisma(数据库 ORM) 持久化，但 Review Workflow(审核流程) 的业务状态修改和审计写入尚未处于同一事务。
4. checksum(校验和)、published immutable(已发布不可变) 和 Agent Profile security policy(安全策略) 都是契约保护点，不能在切换中弱化。
5. 如果某个写事务仍落在 memory(内存)，而查询已走 prisma(数据库)，页面和 API 会读不到刚写入的数据。

因此 P3.2 的结论是：先引入 TransactionManager(事务管理器) / HubUnitOfWork(Hub 工作单元) 设计，再分批切写事务，且每一批都要保证读写同源。

## 2. 当前写事务现状

### 2.1 写事务现状总表

| 写事务 | 当前服务文件 | 当前数据源 | 当前是否写 AuditLog | 是否涉及 checksum | 是否涉及 published immutable | 是否涉及多表事务 | 切换风险 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Asset 创建 | `asset-governance-service.ts` | `HubRepository.assets` | 否 | 否 | 否 | 否 | 需要唯一性从内存扫描改为数据库唯一校验，slug 冲突错误码必须不变 |
| Asset 更新 | `asset-governance-service.ts` | `HubRepository.assets` | 否 | 否 | 是，禁止 published/deprecated/archived 直接改基础信息 | 否 | rejected -> draft 状态恢复需保留；不能允许修改 slug/kind/content |
| Asset Version 创建 | `asset-version-service.ts` | `HubRepository.assetVersions` | 否 | 是，创建时生成 checksum/contentSize | 否，新建 immutable=false | 是，读取 Asset 后写 Version | 需要同 asset 下 version 唯一；archived Asset 阻断要在事务内完成 |
| Asset Version 发布 | `asset-version-service.ts` / `review-workflow-service.ts` | `HubRepository.assetVersions` + `HubRepository.assets` | ReviewWorkflow 路径会写 | 是，发布前重算 checksum | 是，设置 immutable=true | 是，Version + Asset + AuditLog | 最关键，必须事务化，否则可能 Version published 但 Asset.latestVersionId 或 AuditLog 未写 |
| Asset Version 废弃 | `asset-version-service.ts` | `HubRepository.assetVersions` | 否 | 不改变 checksum | 是，published 才能废弃 | 否 | 需要保存旧锁可用语义；不应删除 content |
| Asset 归档 | `asset-governance-service.ts` | `HubRepository.assets` | 否 | 否 | 是，归档后不允许修改/新增版本 | 否 | 后续新版本、新绑定必须读取 archived 状态并阻断 |
| Manifest 创建 | `manifest-governance-service.ts` | `HubRepository.manifests` | 否 | 否 | 否 | 否 | slug 唯一性和 scope/owner 语义要与 schema 一致 |
| Manifest 更新 | `manifest-governance-service.ts` | `HubRepository.manifests` | 否 | 否 | 是，published/deprecated/archived 不允许直接改基础信息 | 否 | rejected -> draft 恢复要保留；不能改 slug |
| Manifest Version 创建 | `manifest-version-service.ts` | `HubRepository.manifestVersions` | 否 | 是，创建后计算 Manifest checksum | 否 | 是，读取 Manifest 后写 Version | 初始 checksum 和 installPolicy(安装策略) 默认值必须与 V2.1 一致 |
| Manifest 绑定 AssetVersion | `manifest-asset-binding-service.ts` | `HubRepository.manifestAssets` + assets + assetVersions + manifestVersions | 否 | 是，绑定后重算 ManifestVersion checksum | 是，目标 AssetVersion 必须 published/immutable | 是，多表读取 + binding 写入 + checksum 更新 | 事务复杂，重复绑定、kind 不一致、archived/deprecated 规则必须原子化 |
| Manifest 解绑 AssetVersion | `manifest-asset-binding-service.ts` | `HubRepository.manifestAssets` + manifestVersions | 否 | 是，解绑后重算 checksum | 是，published ManifestVersion 不允许解绑 | 是，binding 删除 + checksum 更新 | 解绑成功但 checksum 失败会导致导出不一致 |
| Manifest 绑定排序 | `manifest-asset-binding-service.ts` | `HubRepository.manifestAssets` + manifestVersions | 否 | 是，排序后重算 checksum | 是，published ManifestVersion 不允许排序 | 是，多 binding 更新 + checksum 更新 | 部分排序成功会污染 Manifest checksum |
| Manifest Version 发布 | `manifest-version-service.ts` / `review-workflow-service.ts` | manifestVersions + manifests + manifestAssets + assetVersions + assets | ReviewWorkflow 路径会写 | 是，发布前重算 checksum | 是，绑定 AssetVersion 必须 immutable=true | 是，多表校验 + Version + Manifest + AuditLog | 最复杂，必须校验 required asset、published asset、checksum 后再更新 |
| Manifest Version 废弃 | `manifest-version-service.ts` | `HubRepository.manifestVersions` | 否 | 不改变 checksum | 是，只能废弃 published | 否 | deprecated 仍可被旧 lock 使用，不能删除绑定 |
| Manifest 归档 | `manifest-governance-service.ts` | `HubRepository.manifests` | 否 | 否 | 是，归档后不允许新增版本/新推荐命中 | 否 | 归档后所有写入口必须统一阻断 |
| Agent Profile 创建 | `agent-profile-governance-service.ts` | `HubRepository.agentProfiles` | 否 | 是，基于 content 生成 checksum | 否 | 否 | slug + version 唯一，content 安全策略和隐私校验必须先于入库 |
| Agent Profile 更新 | `agent-profile-governance-service.ts` | `HubRepository.agentProfiles` | 否 | 是，content 变更后重算 checksum | 是，published/deprecated/archived 禁止更新 | 否 | rejected -> draft 恢复、rejectedReason 清理要保留 |
| Agent Profile 发布 | `agent-profile-governance-service.ts` / `review-workflow-service.ts` | `HubRepository.agentProfiles` | ReviewWorkflow 路径会写 | 是，发布前重算 checksum | 是，published 后 content 不可直接修改 | 是，Profile 更新 + AuditLog | 安全策略必须与 checksum 同事务校验；审计失败不能发布成功 |
| Agent Profile 废弃 | `agent-profile-governance-service.ts` | `HubRepository.agentProfiles` | 否 | 不改变 checksum | 是，只能废弃 published | 否 | deprecated 旧 lock 可用，不应被新 Manifest 默认选中 |
| Agent Profile 归档 | `agent-profile-governance-service.ts` | `HubRepository.agentProfiles` | 否 | 不改变 checksum | 是，归档后不可修改/export | 否 | 归档后查询、export、绑定选择都必须排除 |
| submit-review | `review-workflow-service.ts` | 对应内存对象 + AuditLogService | 是 | 不修改 checksum | 是，published 不允许提交审核 | 是，状态变化 + AuditLog | 当前状态先改对象后写审计，memory 下无回滚；prisma 下必须同事务 |
| reject | `review-workflow-service.ts` | 对应内存对象 + AuditLogService | 是 | 不修改 checksum | 是，仅 reviewing 可驳回 | 是，状态变化 + AuditLog | reason 必填，审计失败不能保留 rejected 状态 |
| publish | `review-workflow-service.ts` 转调各 publish 服务 | 内存对象 + AuditLogService | 是 | 是 | 是 | 是，业务发布 + AuditLog | 当前业务 publish 成功后再写 audit；prisma 下必须纳入同一事务 |
| AuditLog 写入 | `audit-log-service.ts` | memory 或 Prisma HubAuditLog | 是 | 否 | 否 | 应作为业务事务一部分 | 单独成功或单独失败都会破坏可追溯性 |

### 2.2 当前实现结论

1. 查询链路已经能通过 Repository Port(仓储接口) 双模式读取。
2. 写链路仍直接依赖 `HubRepository` 内存对象，尤其是 `.assets`、`.assetVersions`、`.manifests`、`.manifestVersions`、`.manifestAssets`、`.agentProfiles`。
3. P2 已把 AuditLog(审计日志) 改造成可持久化仓储，但业务状态更新与 AuditLog 写入还没有统一事务。
4. 后续切换必须先补 Repository 写方法和 TransactionManager(事务管理器)，不能在 service(服务) 中直接散落 Prisma Client(Prisma 客户端)。

## 3. Repository Port 缺口分析

### 3.1 AssetRepositoryPort 缺口

当前 `AssetRepositoryPort` 只覆盖查询：

1. `listAssets`
2. `findAssetById`
3. `findAssetBySlug`
4. `listAssetVersions`
5. `findAssetVersionById`
6. `listAssetManifestRefs`

缺少写方法：

1. `createAsset`
2. `updateAssetDraft`
3. `archiveAsset`
4. `createAssetVersion`
5. `updateAssetVersionForPublish`
6. `deprecateAssetVersion`
7. `findAssetVersionByAssetAndVersion`
8. `assertAssetSlugAvailable` 或唯一性查询方法

建议：拆出 `AssetVersionRepositoryPort`，避免 Asset 主表接口过大。

### 3.2 AssetVersionRepositoryPort 是否需要单独拆分

建议新增。原因：

1. Asset 与 AssetVersion 生命周期不同。
2. AssetVersion 发布涉及 checksum、immutable、publishedAt、publishedBy。
3. Manifest 绑定只需要查询 AssetVersion published/immutable/checksum 状态。
4. 后续版本对比、内容读取也会聚焦 AssetVersion。

建议方法：

```ts
export interface AssetVersionRepositoryPort {
  createAssetVersion(input: CreateAssetVersionInput): Promise<HubAssetVersionDetail>;
  updateDraftAssetVersion(input: UpdateDraftAssetVersionInput): Promise<HubAssetVersionDetail>;
  publishAssetVersion(input: PublishAssetVersionInput): Promise<HubAssetVersionDetail>;
  deprecateAssetVersion(input: DeprecateAssetVersionInput): Promise<HubAssetVersionDetail>;
  findAssetVersionByAssetAndId(assetId: string, versionId: string): Promise<HubAssetVersionDetail | null>;
  findAssetVersionByAssetAndVersion(assetId: string, version: string): Promise<HubAssetVersionDetail | null>;
}
```

### 3.3 ManifestRepositoryPort 缺口

当前 `ManifestRepositoryPort` 只覆盖查询：

1. `listManifests`
2. `findManifestById`
3. `findManifestBySlug`
4. `listManifestVersions`
5. `findManifestVersionById`
6. `listManifestAssetBindings`

缺少写方法：

1. `createManifest`
2. `updateManifestDraft`
3. `archiveManifest`
4. `createManifestVersion`
5. `publishManifestVersion`
6. `deprecateManifestVersion`
7. `updateManifestVersionChecksum`

建议：拆出 `ManifestVersionRepositoryPort` 和 `ManifestAssetBindingRepositoryPort`。

### 3.4 ManifestVersionRepositoryPort 是否需要单独拆分

建议新增。原因：

1. Manifest 主表和 ManifestVersion 发布事务不同。
2. ManifestVersion 发布要校验多个 AssetVersion。
3. ManifestVersion checksum 依赖绑定关系排序。
4. Manifest Export(清单导出) 的核心是 published ManifestVersion。

建议方法：

```ts
export interface ManifestVersionRepositoryPort {
  createManifestVersion(input: CreateManifestVersionInput): Promise<HubManifestVersionDetail>;
  publishManifestVersion(input: PublishManifestVersionInput): Promise<HubManifestVersionDetail>;
  deprecateManifestVersion(input: DeprecateManifestVersionInput): Promise<HubManifestVersionDetail>;
  updateManifestVersionChecksum(versionId: string, checksum: string): Promise<HubManifestVersionDetail>;
  findManifestVersionByManifestAndId(manifestId: string, versionId: string): Promise<HubManifestVersionDetail | null>;
}
```

### 3.5 ManifestAssetBindingRepositoryPort 是否需要单独拆分

建议新增。原因：

1. 绑定、解绑、排序都是独立事务热点。
2. 绑定关系与 Asset、AssetVersion、ManifestVersion 都有关联。
3. 需要支持重复绑定校验和批量排序。
4. 后续版本对比、绑定审计、发布前检查都会复用。

建议方法：

```ts
export interface ManifestAssetBindingRepositoryPort {
  createBinding(input: CreateManifestAssetBindingInput): Promise<HubManifestAssetBinding>;
  deleteBinding(manifestVersionId: string, bindingId: string): Promise<void>;
  reorderBindings(manifestVersionId: string, items: Array<{ bindingId: string; order: number }>): Promise<HubManifestAssetBinding[]>;
  findBindingByAssetVersion(manifestVersionId: string, assetVersionId: string): Promise<HubManifestAssetBinding | null>;
  listBindingsForChecksum(manifestVersionId: string): Promise<HubManifestAssetBinding[]>;
}
```

### 3.6 AgentProfileRepositoryPort 缺口

当前只覆盖查询：

1. `listAgentProfiles`
2. `findAgentProfileById`
3. `findAgentProfileBySlugAndVersion`

缺少写方法：

1. `createAgentProfile`
2. `updateAgentProfileDraft`
3. `publishAgentProfile`
4. `deprecateAgentProfile`
5. `archiveAgentProfile`
6. `findAgentProfileBySlugVersionScope`
7. `updateAgentProfileReviewStatus`

建议在 P3.5 补齐，不要提前塞到查询 Port 中。

### 3.7 AuditLogRepositoryPort 是否已经满足写入

基本满足当前 P3.2 设计需要：

1. `createAuditLog`
2. `listAuditLogs`

需要补充的不是字段，而是事务上下文能力：

1. AuditLogRepositoryPort 应支持在 `HubTransactionContext` 中使用 tx client(tx 客户端)。
2. `createAuditLog` 必须仍调用隐私过滤。
3. 审计写入失败必须让事务整体失败。

### 3.8 是否需要 UnitOfWork / TransactionManager

需要。

建议新增：

1. `TransactionManagerPort`：抽象事务执行。
2. `HubTransactionContext`：事务内可用的 repositories(仓储集合)。
3. `HubUnitOfWork`：在 service 中统一进入事务，避免 service 直接依赖 Prisma Client。

建议：

```text
是否需要新增 TransactionManagerPort：需要。
是否需要新增 HubUnitOfWork：需要，可作为 TransactionManager 的领域命名封装。
是否需要 Repository 方法接收 tx 参数：不建议业务 service 传 tx 参数；建议 TransactionManager 创建事务内 repository context。
是否需要封装 prisma.$transaction：需要，放在 PrismaTransactionManager 内。
```

## 4. 事务边界设计

### 4.1 Asset Version 发布事务

必须在同一事务内完成：

1. 校验 Asset 存在。
2. 校验 AssetVersion 存在。
3. 校验当前状态可发布，P3.3 建议保留 draft/reviewing 可发布，P3.6 再统一为 reviewing 优先。
4. 校验 content 非空。
5. 重新计算 checksum。
6. 更新 AssetVersion：`status=published`。
7. 更新 AssetVersion：`immutable=true`。
8. 更新 AssetVersion：`publishedAt`、`publishedBy`、`contentSize`、`checksum`。
9. 更新 Asset：`latestVersionId`。
10. 更新 Asset：`status=published`、`updatedAt`、`updatedBy`。
11. 写 AuditLog：`targetType=asset-version`、`action=publish`。
12. 事务失败整体回滚。

伪代码：

```ts
await txManager.runInTransaction(async (tx) => {
  const asset = await tx.assets.findAssetById(assetId);
  const version = await tx.assetVersions.findAssetVersionByAssetAndId(assetId, versionId);
  assertCanPublishAssetVersion(asset, version);
  const checksum = sha256Text(version.content);
  const published = await tx.assetVersions.publishAssetVersion({ assetId, versionId, checksum, publishedBy: "system" });
  await tx.assets.markAssetPublished({ assetId, latestVersionId: versionId });
  await tx.auditLogs.createAuditLog({ targetType: "asset-version", targetId: versionId, action: "publish" });
  return published;
});
```

### 4.2 Manifest Version 发布事务

必须在同一事务内完成：

1. 校验 Manifest 存在。
2. 校验 ManifestVersion 存在。
3. 校验状态可发布。
4. 查询所有绑定关系，按 `order` 升序。
5. 校验至少一个 required AssetVersion。
6. 校验所有绑定的 AssetVersion 都是 published。
7. 校验所有绑定的 AssetVersion `immutable=true`。
8. 校验所有绑定的 AssetVersion checksum 存在。
9. 重新计算 Manifest checksum。
10. 更新 ManifestVersion：`status=published`。
11. 设置 `publishedAt`、`publishedBy`、`checksum`。
12. 更新 Manifest：`latestVersionId`。
13. 更新 Manifest：`status=published`、`updatedAt`、`updatedBy`。
14. 写 AuditLog：`targetType=manifest-version`、`action=publish`。
15. 事务失败整体回滚。

注意：

1. deprecated AssetVersion 是否允许旧 lock export，取决于 ManifestVersion 已发布时是否已锁定旧绑定；新绑定禁止 deprecated。
2. 发布时不应删除或重写绑定关系。
3. checksum 输入必须包含 ManifestVersion 基础字段和有序绑定摘要。

### 4.3 Manifest Asset 绑定事务

必须在同一事务内完成：

1. 校验 ManifestVersion 是 draft/reviewing。
2. 校验 Manifest 未 archived。
3. 校验 Asset 存在。
4. 校验 Asset 未 archived。
5. 校验 AssetVersion 存在且属于 Asset。
6. 校验 AssetVersion 是 published。
7. 校验 AssetVersion `immutable=true`。
8. 校验 AssetVersion checksum 存在。
9. 校验 Asset / AssetVersion 不是 deprecated 新绑定目标。
10. 校验不重复绑定同一个 AssetVersion。
11. 校验 kind 与 Asset.kind 一致。
12. 创建绑定关系。
13. 重算 ManifestVersion checksum。
14. 写 AuditLog：`targetType=manifest-version`、`action=bind`。
15. 事务失败整体回滚。

解绑事务：

1. 校验 ManifestVersion 是 draft/reviewing。
2. 校验 bindingId 属于当前 ManifestVersion。
3. 删除绑定。
4. 重算 checksum。
5. 写 AuditLog：`action=unbind`。
6. 事务失败整体回滚。

排序事务：

1. 校验 ManifestVersion 是 draft/reviewing。
2. 校验所有 bindingId 属于当前 ManifestVersion。
3. 校验 order 是数字。
4. 批量更新排序。
5. 重算 checksum。
6. 写 AuditLog：`action=reorder`。
7. 事务失败整体回滚。

### 4.4 Agent Profile 发布事务

必须在同一事务内完成：

1. 校验 Agent Profile 存在。
2. 校验状态可发布。
3. 校验 content 存在。
4. 校验安全策略：
   - deniedTools 包含 upload-source。
   - deniedTools 包含 deploy。
   - deniedTools 包含 push。
   - deniedTools 包含 merge。
   - `contextScope.allowSourceCode=false`。
   - `contextScope.allowAbsolutePath=false`。
   - `approvalPolicy.beforePush=true`。
   - `approvalPolicy.beforeMerge=true`。
   - `approvalPolicy.highRiskAlwaysManual=true`。
5. 重新计算 checksum。
6. 更新 `status=published`。
7. 设置 `publishedAt`、`publishedBy`、`updatedAt`。
8. 写 AuditLog：`targetType=agent-profile`、`action=publish`。
9. 事务失败整体回滚。

### 4.5 Review Workflow 状态流转事务

必须保证：

1. submit-review 状态变化和 AuditLog 一致。
2. reject 状态变化和 AuditLog 一致。
3. publish 状态变化和 AuditLog 一致。
4. 审计失败时业务状态不能成功提交。
5. 业务状态失败时审计不能单独写入成功。

建议 P3.6 将 ReviewWorkflowService 改造成只协调领域 service 的事务方法：

```text
ReviewWorkflowService
  -> TransactionManager.runInTransaction
    -> target repository 更新状态
    -> auditLogs.createAuditLog
```

不建议 ReviewWorkflowService 在 Prisma 模式下继续直接改内存对象。

## 5. TransactionManager 设计

建议新增接口：

```ts
export interface TransactionManagerPort {
  runInTransaction<T>(handler: (tx: HubTransactionContext) => Promise<T>): Promise<T>;
}

export interface HubTransactionContext {
  assets: AssetRepositoryPort;
  assetVersions: AssetVersionRepositoryPort;
  manifests: ManifestRepositoryPort;
  manifestVersions: ManifestVersionRepositoryPort;
  manifestAssetBindings: ManifestAssetBindingRepositoryPort;
  agentProfiles: AgentProfileRepositoryPort;
  auditLogs: AuditLogRepositoryPort;
}
```

### 5.1 memory 模式如何模拟事务

memory(内存) 模式建议使用快照回滚：

1. 事务开始前深拷贝当前 HubRepository 状态。
2. handler 成功后保留修改。
3. handler 抛错时恢复快照。
4. AuditLog 内存仓储也纳入快照。
5. 单元测试可验证“业务失败不写审计”“审计失败回滚业务状态”。

注意：memory 模式的事务只是测试模拟，不代表多线程安全。

### 5.2 prisma 模式如何使用 prisma.$transaction

Prisma(数据库 ORM) 模式建议：

```ts
class PrismaTransactionManager implements TransactionManagerPort {
  constructor(private readonly prisma: PrismaClient) {}

  runInTransaction<T>(handler: (tx: HubTransactionContext) => Promise<T>): Promise<T> {
    return this.prisma.$transaction(async (client) => {
      return handler(createPrismaTransactionContext(client));
    });
  }
}
```

要求：

1. `createPrismaTransactionContext(client)` 使用 transaction client(tx 客户端) 创建各 repository。
2. service 只拿到 `HubTransactionContext`，不接触 Prisma Client。
3. AuditLogRepository 在事务内使用同一个 tx client。
4. 事务内不做长时间外部 I/O，避免锁时间过长。

### 5.3 Repository 如何接受 tx client

不建议每个方法显式接收 `tx` 参数，因为会污染 service 调用签名。

建议：

1. Repository 构造时注入 client。
2. 普通模式注入 Prisma root client。
3. 事务模式注入 Prisma transaction client。
4. 对 service 来说二者都是同一个 Port。

### 5.4 如何避免 service 直接依赖 Prisma Client

规则：

1. service 只依赖 Port 或 TransactionManager。
2. `@/lib/prisma` 只允许在 Provider / PrismaTransactionManager / PrismaRepository 中出现。
3. 测试通过 mock repository 或 mock transaction manager 注入。
4. route 只做参数解析、调用 service、返回 ApiResponse。

### 5.5 如何保证测试可 mock

测试策略：

1. 用 `MemoryTransactionManager` 做大部分业务事务测试。
2. 用 mock Prisma Client 验证 `$transaction` 被调用。
3. 用 contract test(契约测试) 对比 memory/prisma repository 返回结构。
4. 用失败注入测试 AuditLog 写入失败时回滚业务状态。

## 6. 双模式切换策略

必须支持：

```text
HUB_REPOSITORY_MODE=memory
HUB_REPOSITORY_MODE=prisma
```

### 6.1 memory 模式

用途：

1. 单元测试。
2. 本地快速测试。
3. 无数据库环境下的演示。

要求：

1. 读写都走 InMemory Repository。
2. TransactionManager 使用 MemoryTransactionManager。
3. 不连接数据库。
4. 行为必须尽量贴近 prisma 模式。

### 6.2 prisma 模式

用途：

1. 开发库联调。
2. 试点环境。
3. 生产化基座验证。

要求：

1. 读写必须统一走 Prisma Repository。
2. TransactionManager 使用 PrismaTransactionManager。
3. 如果某个写事务尚未支持 Prisma，必须阻断启动或返回中文错误。
4. 禁止静默降级为 memory。
5. 禁止出现读 prisma、写 memory 的混用。

### 6.3 过渡期启动保护

在 P3.3-P3.6 分批期间，建议 Provider 支持能力声明：

```ts
export interface HubRepositoryCapabilities {
  assetWrite: boolean;
  manifestWrite: boolean;
  agentProfileWrite: boolean;
  reviewWorkflowWrite: boolean;
}
```

如果 `HUB_REPOSITORY_MODE=prisma` 且调用尚未切换的写事务：

1. 返回中文错误。
2. 错误码建议：`PRISMA_WRITE_NOT_READY`。
3. 不自动回落到 memory。

2. TransactionManager(事务管理器) 单元测试：验证成功提交、失败回滚。
3. memory 事务模拟测试：验证内存快照回滚。
4. prisma transaction mock(Prisma 事务模拟) 测试：验证 `$transaction` 被使用且 tx client 贯穿 repositories。
5. Asset 写事务测试：创建、更新、版本创建、发布、废弃、归档。
6. Manifest 写事务测试：创建、版本创建、绑定、解绑、排序、发布、废弃、归档。
7. Agent Profile 写事务测试：创建、更新、发布、废弃、归档、安全策略。
8. Review Workflow 事务一致性测试：submit-review、reject、publish。
9. AuditLog 与业务状态一致性测试：业务失败无审计、审计失败业务回滚。
10. 读写同源测试：memory 模式读写都 memory，prisma 模式读写都 prisma。
11. 隐私字段不入库测试：sourceCode、rawPrompt、rawResponse、/Users/、token、secret。
12. checksum 稳定性测试：相同内容 checksum 稳定，内容变化 checksum 变化。
13. published immutable 测试：published content / binding 不可直接改。

## 9. 兼容性保护

P3.3-P3.7 必须持续保护：

1. V1.1 Hub API 不变。
2. br-ai-spec 契约不变。
3. V2.1 页面不变。
4. ApiResponse(统一响应结构) 不变。
5. Manifest Export(清单导出) 不变。
6. Asset Content(资产内容) 不变。
7. Agent Profile Export(智能体配置导出) 不变。
8. Runtime Feedback(运行反馈) 隐私规则不变。
9. AuditLog(审计日志) 隐私规则不变。
10. published immutable(已发布不可变) 不变。

禁止通过以下方式“解决”兼容问题：

1. 放宽隐私校验。
2. 放宽 checksum 校验。
3. 允许直接修改 published 内容或绑定。
4. 修改 br-ai-spec 消费结构。
5. 静默降级到 memory 模式。

## 10. 风险点

1. 读写数据源不一致：查询已支持 prisma，但写仍 memory，必须用能力开关阻断混用。
2. Prisma transaction(Prisma 事务) 粒度过大：发布事务如果包含过多查询和计算，会拉长锁时间。
3. Manifest 绑定关系事务复杂：绑定、解绑、排序、checksum 必须原子化。
4. AuditLog 写入失败导致业务阻断：这是正确策略，但需要中文错误和清晰回滚测试。
5. checksum 在事务内外不一致：checksum 输入必须固定排序和字段集合。
6. JSON 字段映射不稳定：tags、installPolicy、content、policy 等字段必须通过 mapper 和 schema 校验。
7. Date 类型转换影响 API 响应：Prisma Date 必须继续转 ISO string。
8. seed 数据不一致：memory seed 与数据库 seed 需要逐步统一。
9. 测试环境没有真实数据库：P3.3-P3.6 先用 mock 和 memory，P3.7 再做开发库 smoke。
10. memory 模式和 prisma 模式行为不一致：contract test 必须覆盖错误码、响应字段、状态流转。

## 12. P3.2 结论

P3.2 设计结论：

1. 写事务不能直接切换到 Prisma Repository。
2. 必须先补 TransactionManagerPort 和 HubTransactionContext。
3. 必须将 AuditLog 写入纳入同一事务。
4. 必须按 Asset -> Manifest -> Agent Profile -> Review Workflow -> 真实开发库 smoke 的顺序分批切换。
5. `HUB_REPOSITORY_MODE=prisma` 不允许读 prisma、写 memory 混用。
6. 可以进入 P3.3，但 P3.3 只应切 Asset 写事务，不应同时切 Manifest / Agent Profile。
