# V2.1 Hub Asset Governance 实施方案

## 1. V2.1 总目标

V2.1 的目标是把 `skill-q-platform` 从 Hub API(资产中心接口)最小闭环升级为团队可用的资产治理平台。V1.1 已经证明 `br-ai-spec` 可以消费 Hub(资产中心)，`br-ai-spec-visual` 可以接收运行态数据；V2.1 不再优先补更多执行能力，而是让团队能在 Hub(资产中心)里看见、管理、审核、发布、废弃和追踪资产。

V2.1 和 V1.1 的关系：

1. V1.1 是契约闭环：Manifest Recommend API(清单推荐接口)、Manifest Export API(清单导出接口)、Asset Content API(资产内容接口)、Agent Profile Export API(智能体画像导出接口)、Install Record API(安装记录接口)、Runtime Feedback API(运行反馈接口)已经可用。
2. V2.1 是治理产品化：围绕 Asset(资产)、Asset Version(资产版本)、Manifest(清单)、Manifest Version(清单版本)、Agent Profile(智能体画像)、审核发布、废弃归档、搜索筛选、checksum(校验和)展示、seed(种子数据)管理补齐后台产品能力。
3. V2.1 必须保持 V1.1 对 `br-ai-spec` 的 API(接口)契约稳定，不因后台治理改造破坏现有 init(初始化)、sync(同步)、runtime-feedback(运行反馈)链路。

本轮只做方案设计，不实现 UI(用户界面)、API(接口)、Prisma schema(数据库模型)或业务逻辑。

## 2. 当前代码结构分析

当前项目是 Next.js(全栈前端框架) + React(前端框架) + Prisma(数据库 ORM) + MySQL/MariaDB(关系型数据库) 的资产 Hub(资产中心)。核心目录如下：

| 区域 | 当前职责 | V2.1 关注点 |
| --- | --- | --- |
| `src/app/api/hub/*` | V1.1 Hub API(资产中心接口)路由 | 保持契约稳定，未来可从内存仓库切到 Prisma(数据库 ORM)仓库 |
| `src/server/hub/*` | Hub(资产中心)服务层、类型、checksum(校验和)、隐私校验、seed(种子数据) | 补治理服务边界：审核、状态流转、版本对比、搜索筛选 |
| `prisma/schema.prisma` | 当前业务资源站模型和 Hub(资产中心)最小表 | 评估 V2.1 字段、migration(数据库迁移)、seed(种子数据)需求 |
| `src/app/admin/(protected)/*` | 现有后台页面：skills(技能)、rules(规则)、roles(角色)、scenarios(场景)、agents(智能体)、config(配置) | 新增治理后台信息架构，但本轮不实现 |
| `src/components/admin/*` | 后台表格、筛选、管理组件 | 后续承接 Asset(资产)、Manifest(清单)、Agent Profile(智能体画像)治理视图 |
| `tests/unit/*`、`tests/integration/*` | Hub(资产中心)服务和 API(接口)契约测试 | V2.1 需要扩展审核流、状态流、搜索筛选、版本对比测试 |

当前 `src/server/hub` 以 `HubRepository`(内存仓库)承载 V1.1 契约测试，`defaultHubRepository`(默认内存仓库)通过 seed(种子数据)生成 published(已发布) Manifest(清单)、Asset(资产)和 Agent Profile(智能体画像)。这满足 V1.1 smoke test(冒烟测试)，但 V2.1 作为团队平台需要落到 Prisma(数据库 ORM)持久层。

## 3. V1.1 当前基础能力

V1.1 已完成的基础能力如下：

1. Manifest Recommend API(清单推荐接口)：`POST /api/hub/manifests/recommend`，按 `projectFacts`(项目事实)推荐已发布 Manifest(清单)。
2. Manifest Export API(清单导出接口)：`GET /api/hub/manifests/[manifestId]/export`，导出 manifest checksum(清单校验和)、assets(资产索引)、agentProfiles(智能体画像索引)和 installPolicy(安装策略)。
3. Asset Content API(资产内容接口)：`GET /api/hub/assets/[slug]/content`，按 slug(标识)和 version(版本)读取 published(已发布)资产正文和 checksum(校验和)。
4. Agent Profile Export API(智能体画像导出接口)：`GET /api/hub/agent-profiles/[slug]/export`，导出执行器、工具权限、上下文范围、模型策略和 checksum(校验和)。
5. Install Record API(安装记录接口)：`POST /api/hub/install-records`，接收 `br-ai-spec` init(初始化)或 sync(同步)后的安装上报。
6. Runtime Feedback API(运行反馈接口)：`POST /api/hub/runtime-feedback`，接收资产使用结果、执行器、耗时和问题摘要，并拒绝源码、rawPrompt(原始提示词)、rawResponse(原始响应)等隐私违规字段。
7. `br-ai-spec` 已可消费 Hub(资产中心)：可调用 recommend/export/content/profile/install-record/runtime-feedback，并把资产缓存到本地全局缓存。
8. `br-ai-spec-visual` 已可接收运行态数据：Collector API(采集接口)支持 project-state(项目状态)、run-event(运行事件)、history(历史摘要)、incident(事故)上报。

## 4. V2.1 不做什么

V2.1 暂不做以下内容，避免从治理平台改造成大而全自动化平台：

1. AI 工程资产生成器。
2. 真实 Codex(代码智能体)自动编码。
3. OpenClaw(远程协作入口)。
4. 钉钉机器人。
5. 复杂组织架构。
6. 复杂报表。
7. 自动 PR(拉取请求) / push(推送) / merge(合并)。
8. 复杂权限系统。

V2.1 可以预留字段或扩展点，但不能把上述能力做成主线实现。

## 5. 产品模块规划

| 模块 | 目标 | V2.1 范围 |
| --- | --- | --- |
| Asset 资产管理 | 统一管理 rule(规则)、skill(技能)、role(角色)、flow(流程)、scenario(场景)、agent-profile(智能体画像)等资产 | 列表、详情、状态、scope(作用域)、owner(所有者)、checksum(校验和)摘要 |
| Asset Version 版本管理 | 保证发布后不可变，修改必须新版本 | 版本列表、版本详情、latest(最新)识别、发布状态、immutable(不可变)展示 |
| Manifest 管理 | 管理技术栈安装清单身份 | 列表、详情、scope(作用域)、状态、推荐标签、适配技术栈 |
| Manifest Version 管理 | 管理 Manifest(清单)版本和 installPolicy(安装策略) | 版本列表、checksum(校验和)、兼容性、默认执行器展示 |
| Manifest 绑定 Asset | 管理 Manifest(清单)引用哪些资产版本 | 绑定列表、required(必需)、loadWhen(加载时机)、order(顺序)、只允许绑定 published(已发布)资产 |
| Agent Profile 管理 | 管理执行器选择、工具权限和风险等级 | 列表、详情、版本、riskLevel(风险等级)、allowedTools(允许工具)、deniedTools(拒绝工具) |
| 发布流程 | 从 draft(草稿)提交 reviewing(审核中)，审核通过后 published(已发布) | 资产和清单统一状态机，写入审计记录 |
| 废弃 / 归档流程 | published(已发布)资产可 deprecated(废弃)，最终 archived(归档) | 废弃后不再进入新 Manifest(清单)，归档后只读展示 |
| 资产搜索 | 团队按 slug(标识)、name(名称)、kind(类型)、description(描述)快速定位 | 搜索接口和后台列表筛选方案 |
| 资产筛选 | 按 kind(类型)、status(状态)、scope(作用域)、owner(所有者)、checksum(校验和存在性)筛选 | 后台表格筛选方案 |
| 资产详情 | 看见资产元信息、版本、被哪些 Manifest(清单)引用、安装/运行反馈 | 聚合详情，不编辑已发布正文 |
| 版本对比 | 对比两个资产版本或 Manifest(清单)版本变化 | V2.1 设计文本 diff(差异)与 JSON diff(结构差异)，不做复杂可视化 |
| checksum 展示 | 明确每个发布版本 checksum(校验和)，支持复制与校验 | 列表摘要 + 详情完整值 |
| seed 数据管理 | 管理演示和初始化种子资产，减少环境漂移 | seed(种子数据)清单、校验脚本、版本冻结说明 |

建议后台信息架构先按四个一级入口组织：

1. 资产治理：Asset(资产)、Asset Version(资产版本)、版本对比、被引用关系。
2. 清单治理：Manifest(清单)、Manifest Version(清单版本)、Manifest 绑定 Asset(清单绑定资产)。
3. Agent Profile(智能体画像)：执行器策略、工具权限、风险等级。
4. 发布与审计：待审核、已驳回、废弃归档、AuditLog(审计日志)。

## 7. 状态流转设计

V2.1 统一 Asset(资产)、Asset Version(资产版本)、Manifest(清单)、Manifest Version(清单版本)、Agent Profile(智能体画像)的治理状态。必须支持：

```text
draft -> reviewing -> published
draft -> archived
reviewing -> rejected
published -> deprecated
published -> archived
deprecated -> archived
```

状态含义：

| 状态 | 含义 | 关键规则 |
| --- | --- | --- |
| draft(草稿) | 可编辑、未提交审核 | 不允许被 Manifest Export(清单导出)消费 |
| reviewing(审核中) | 已提交审核，等待审核人处理 | 内容原则上冻结，允许撤回需单独设计 |
| rejected(已驳回) | 审核不通过 | 必须记录驳回原因，可从 rejected(已驳回)复制为新 draft(草稿) |
| published(已发布) | 可被导出和安装 | content(正文)不可修改，checksum(校验和)必须存在 |
| deprecated(已废弃) | 老项目可继续锁定使用，新 Manifest(清单)不应默认引用 | 导出历史版本允许，新建绑定默认阻断 |
| archived(已归档) | 只读存档 | 不允许编辑、审核、发布、绑定 |

状态流转守卫：

1. `published`(已发布)前必须有 checksum(校验和)。
2. `published`(已发布)版本必须 `immutable=true`(不可变)。
3. Manifest Version(清单版本)只能绑定 `published`(已发布)资产版本。
4. `deprecated`(已废弃)资产不允许被新 Manifest Version(清单版本)默认引用。
5. 任意审核、发布、废弃、归档动作必须写 AuditLog(审计日志)。
6. 状态流转失败必须返回中文错误和稳定 Error Code(错误码)。

## 8. API 与服务层规划

V2.1 API(接口)分两类推进。

对外契约 API(接口)保持稳定：

1. `POST /api/hub/manifests/recommend`
2. `GET /api/hub/manifests/[manifestId]/export`
3. `GET /api/hub/assets/[slug]/content`
4. `GET /api/hub/agent-profiles/[slug]/export`
5. `POST /api/hub/install-records`
6. `POST /api/hub/runtime-feedback`

后台治理 API(接口)后续新增，但 V2.1 必须先设计清楚：

1. Asset(资产)列表、详情、版本列表、版本对比。
2. Manifest(清单)列表、详情、版本列表、绑定资产。
3. Agent Profile(智能体画像)列表、详情、版本策略。
4. submit-review(提交审核)、approve(通过)、reject(驳回)、deprecate(废弃)、archive(归档)动作。
5. AuditLog(审计日志)查询。

服务层建议拆分：

| Service(服务) | 职责 |
| --- | --- |
| `AssetGovernanceService`(资产治理服务) | Asset(资产)搜索、筛选、详情、状态流转 |
| `AssetVersionService`(资产版本服务) | 版本创建、发布、不可变校验、版本对比 |
| `ManifestGovernanceService`(清单治理服务) | Manifest(清单)搜索、筛选、版本管理 |
| `ManifestAssetBindingService`(清单资产绑定服务) | 绑定 published(已发布)资产、排序、loadWhen(加载时机) |
| `AssetReviewService`(资产审核服务) | 提交审核、通过、驳回、审核记录 |
| `AuditLogService`(审计日志服务) | 所有治理动作留痕 |
| `HubPrismaRepository`(Hub 数据库仓库) | 替代或包裹当前 `HubRepository`(内存仓库)，逐步接入 Prisma(数据库 ORM) |

## 9. 测试规划

V2.1 每个核心模块必须补测试。建议覆盖：

1. Unit Test(单元测试)：状态流转、不可变校验、checksum(校验和)必填、版本对比、搜索筛选参数。
2. Integration Test(集成测试)：后台治理 API(接口)到 Prisma(数据库 ORM)仓库，Manifest Export(清单导出)继续只导出 published(已发布)资产。
3. Contract Test(契约测试)：现有 `tests/integration/hub-contract.test.ts` 必须保持通过。
4. Privacy Test(隐私测试)：Install Record(安装记录)和 Runtime Feedback(运行反馈)继续拒绝源码、绝对路径、rawPrompt(原始提示词)、rawResponse(原始响应)、token(令牌)。
5. Regression Test(回归测试)：V2.1 改造后 `br-ai-spec` 仍可 recommend/export/content/profile/install-record/runtime-feedback。

## 10. 安全与隐私边界

V2.1 继续遵守以下边界：

1. Hub(资产中心)不接收目标项目源码。
2. Hub(资产中心)不接收完整 prompt(提示词)和 response(响应)。
3. 已发布资产正文不可修改，只能发布新版本。
4. 后台治理动作必须审计。
5. 不把 Codex(代码智能体)、Cursor(编辑器智能体)、Claude Code(代码智能体)写死为唯一执行器；Agent Profile(智能体画像)里只表达可选执行器策略。
6. 不绕过 `.ai-spec/ai-spec.lock.json`，Hub(资产中心)只提供事实源和 checksum(校验和)，项目侧仍以 lock(锁文件)保护安装资产。

## 11. 分阶段实施建议

V2.1 不一次性实现全部内容，建议拆成 5 个小阶段：

1. 阶段一：Prisma(数据库 ORM)字段和 seed(种子数据)方案评审，仅补治理必要字段和迁移计划。
2. 阶段二：HubPrismaRepository(数据库仓库)接入，只替换后台治理查询，不动 V1.1 对外契约。
3. 阶段三：Asset(资产)与 Asset Version(资产版本)后台列表、详情、状态展示。
4. 阶段四：Manifest(清单)、Manifest Version(清单版本)、Manifest 绑定 Asset(清单绑定资产)治理。
5. 阶段五：审核发布、废弃归档、AuditLog(审计日志)、AssetReview(资产审核)闭环。

每个阶段都要保留可回归验收口径，不能一次性混入 Asset Factory(资产工厂)、复杂权限或复杂报表。

## 12. V2.1 验收标准

V2.1 完成后，应满足：

1. 后台能查看 Asset(资产)、Asset Version(资产版本)、Manifest(清单)、Manifest Version(清单版本)、Agent Profile(智能体画像)。
2. 后台能按 kind(类型)、status(状态)、scope(作用域)、owner(所有者)、slug(标识)、name(名称)搜索筛选。
3. Asset(资产)详情能看到版本、checksum(校验和)、被 Manifest(清单)引用关系、安装和运行反馈摘要。
4. Manifest(清单)详情能看到版本、绑定资产、installPolicy(安装策略)、checksum(校验和)。
5. 发布后版本不可修改，修改必须新建版本。
6. 状态流转符合本方案定义。
7. 审核发布、驳回、废弃、归档动作有 AuditLog(审计日志)。
8. V1.1 Hub API(资产中心接口)契约测试继续通过。
9. `br-ai-spec` 可继续消费 Hub(资产中心)。
10. `br-ai-spec-visual` 可继续接收运行态数据，并可在后续通过 Runtime Feedback(运行反馈)关联资产治理指标。

## 13. 本轮结论

V2.1 的关键不是新增自动化执行，而是把 V1.1 已跑通的 Hub(资产中心)契约沉淀成团队可治理、可审计、可发布、可回滚的产品能力。实施时应优先保护 V1.1 对外 API(接口)契约，逐步把当前内存 seed(种子数据)支撑的最小闭环迁移到 Prisma(数据库 ORM)持久层，并围绕 Asset(资产)、Manifest(清单)、Agent Profile(智能体画像)建立清晰的状态流、版本流和审计流。
