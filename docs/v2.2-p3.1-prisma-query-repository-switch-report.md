# V2.2 P3.1 Prisma 查询仓储切换实施报告

## 1. P3.1 目标

V2.2 P3.1 的目标是只切换 Hub 管理后台查询链路，让 Asset、Manifest、Agent Profile 查询服务支持通过 Repository Port 读取数据：

- `HUB_REPOSITORY_MODE=memory` 时保持 V2.1 内存仓储行为。
- `HUB_REPOSITORY_MODE=prisma` 时走 Prisma Repository 查询。
- 不切换创建、更新、发布、审核、绑定、解绑、排序、归档等写事务。
- 不改变 V2.1 页面和 API 响应结构。
- 不破坏 V1.1 Hub API 与 br-ai-spec 契约。

## 2. 修改范围

本轮修改范围：

- 新增 Hub Repository Provider。
- 改造 AssetQueryService 查询链路。
- 改造 ManifestQueryService 查询链路。
- 改造 AgentProfileQueryService 查询链路。
- Admin 查询 API 改为等待异步查询服务。
- 补充 memory / prisma 双模式查询测试。
- 补充 admin 查询 API 兼容集成测试。

本轮未修改：

- Prisma schema。
- migration。
- package.json。
- Asset / Manifest / Agent Profile 写事务。
- V1.1 Hub API 响应结构。

## 3. Repository Provider 说明

新增：

```text
src/server/hub/repositories/hub-repository-provider.ts
```

能力：

- 支持 `HUB_REPOSITORY_MODE=memory`。
- 支持 `HUB_REPOSITORY_MODE=prisma`。
- 默认模式为 `memory`。
- `memory` 模式使用 `defaultHubRepository`，保持现有页面和测试的内存行为。
- `prisma` 模式通过 Prisma Client 构造 `PrismaHubRepository`。
- 显式 `createHubRepositoryProvider({ mode: "prisma" })` 未注入 Prisma Client 时返回中文错误。
- 业务查询服务不直接散落 Prisma Client 调用。

## 4. Asset 查询链路切换说明

改造：

```text
src/server/hub/asset-query-service.ts
```

结果：

- 支持注入 `AssetRepositoryPort`。
- 兼容旧的 `HubRepository` 构造参数，自动包装为 `InMemoryHubRepositoryAdapter`。
- 默认构造时走 `getHubRepositoryProvider()`。
- `list` 通过 repository 查询。
- `detail` 通过 repository 查询 Asset、AssetVersion 和 Manifest 引用。
- `listAssetVersions` 通过 repository 查询。
- `findAssetVersionById` 通过 repository 查询。
- 列表和详情仍不返回 AssetVersion content 正文。
- 返回结构保持 V2.1 兼容。

## 7. memory 模式行为

`memory` 模式仍使用 V2.1 的内存仓储数据：

- Admin 查询 API 默认不需要数据库。
- 现有测试默认不需要 Prisma Client。
- 写事务仍写入 `defaultHubRepository`。
- 查询服务默认读取同一个 `defaultHubRepository`。

## 8. prisma 模式行为

`prisma` 模式通过 `PrismaHubRepository` 查询：

- Asset 查询走 `PrismaAssetRepository`。
- Manifest 查询走 `PrismaManifestRepository`。
- Agent Profile 查询走 `PrismaAgentProfileRepository`。
- Prisma 原始对象必须经过 mapper 转换。
- mapper 不暴露 `sourceCode`、`rawPrompt`、`rawResponse`、`/Users/` 等敏感内容。

当前真实数据库联调仍建议在后续 P3.2 / P7 使用开发库执行。

## 19. 风险点

- Prisma 模式真实数据库需要先确保 V2.1 / V2.2 migration 已在开发库应用。
- 当前 P3.1 仅切查询链路，若写事务仍写内存、查询切到 Prisma，在同一环境中可能出现读写数据源不一致，因此生产化切换需要按 P3.2 继续推进写事务。
- Agent Profile 的 `defaultExecutor` 在 Prisma 查询中仍依赖 content JSON 解析和 mapper 过滤，复杂 JSON 查询后续可在真实数据库联调时进一步优化。

## 20. 是否可以进入 V2.2 P3.2 写事务切换设计

可以。

建议 P3.2 先做写事务切换设计和事务边界确认，再分批切换 Asset / Manifest / Agent Profile 写链路，避免读写数据源不一致。
